# KoreaMate 第八阶段 8B：长期偏好 Memory 设计

## 目标

让 KoreaMate 在不打断旅行规划的前提下，自动记住对未来行程长期有价值的用户偏好，并在后续规划中作为默认值使用。游客可以使用 Memory，登录后自动归并到账户。用户始终可以查看、删除或用自然语言要求遗忘偏好。

Memory 只降低重复输入，不替用户锁死选择。本次对话的明确表达永远优先于长期偏好。

## 第一版记忆范围

只保存以下五类稳定偏好：

1. `departure_city`：常用出发城市，如成都、上海。
2. `budget_level`：默认预算档位，取 `economy`、`balanced`、`comfortable`。
3. `pace`：出行节奏，取 `relaxed`、`balanced`、`packed`。
4. `interest`：长期兴趣，可有多项，如美食、购物、韩剧、历史、自然。
5. `constraint`：长期限制，可有多项，如不吃辣、素食、轮椅出行、避免长距离步行。

不保存具体出发日期、单次同行人数、某次目的地、临时报价、航班、酒店和完整对话摘要。具体金额仍保留在当前行程需求中；长期 Memory 只保存预算档位，避免把一次旅行金额错误套用到不同天数或人数。

## 识别与保存原则

用户不需要明确说“记住”。系统从旅行对话的每条用户消息中异步提取候选偏好，例如：

- “我一般从成都出发” → `departure_city=成都`
- “我不喜欢赶行程” → `pace=relaxed`
- “我比较在意性价比” → `budget_level=balanced`
- “我喜欢咖啡店和韩剧取景地” → 两条 `interest`
- “我不吃辣” → `constraint=不吃辣`

AI 只负责输出结构化候选；普通程序通过共享 Schema 校验类型、键、值、长度和数量，再决定是否写入。无法归入五类、置信度不足或明显只针对本次旅行的内容不保存。

保存成功后，在正常回答末尾或独立轻提示中显示一行，例如“已记住：偏好轻松行程”。提示不要求用户确认，也不阻塞当前规划。

## 数据模型

新增 `UserMemory`：

```text
id
kind
value
normalizedValue
confidence
sourceMessageId
userId nullable
guestId nullable
createdAt
updatedAt
lastConfirmedAt nullable
```

约束：

- `userId` 和 `guestId` 必须且只能存在一个。
- `departure_city`、`budget_level`、`pace` 对每个身份和 kind 只保留一条启用记录，新值覆盖旧值。
- `interest`、`constraint` 可有多条，按 `normalizedValue` 去重。
- `value` 最长 120 字符，`normalizedValue` 最长 120 字符。
- `confidence` 范围为 0 到 1；第一版只有大于等于 0.8 的候选自动保存。
- 来源消息删除时 Memory 保留，但 `sourceMessageId` 置空；用户、游客删除时级联删除。

第一版不保留完整版本历史或软删除状态。用户删除后记录直接移除；后续只有用户再次明确表达同一偏好时才可重新建立。

## 合并与规划优先级

规划输入按以下固定顺序合并：

```text
本次消息明确输入
  > 当前 TripRequirement 已确认信息
  > 长期 Memory
  > 系统默认值
```

Memory 只填充缺失字段，不覆盖当前行程已有值：

- `departure_city` 填充出发城市。
- `pace` 填充行程节奏。
- `interest` 与本次兴趣去重合并；本次明确说“不想购物”等否定表达会排除对应长期兴趣。
- `constraint` 默认合并进入当前限制；本次明确解除的限制除外。
- `budget_level` 转换为给 Planner 的文字偏好，不直接生成固定金额。

Planner 的输入中加入独立 `memory` 区块，和当前 `requirements` 分开，便于调试并避免模型把长期偏好误认为本次明确要求。

## 冲突和游客登录归并

同一身份的新偏好与旧偏好冲突时：

- 单值类型直接以新值替代旧值。
- 多值类型归一化后去重追加。
- 明确否定或“忘掉……”走删除流程，不保存为反向偏好。

游客登录后，在同一个数据库事务中归并：

- 单值类型：账户已有值优先；账户没有时采用游客值。
- 多值类型：按 kind 和 `normalizedValue` 去重合并。
- 重复记录保留账户记录。
- 对话、收藏和 Memory 归并必须一起成功或一起回滚。

## API

新增：

```text
GET    /api/v1/memories
DELETE /api/v1/memories/:id
```

第一版不提供通用手工创建或编辑 API，避免客户端绕过提取与校验。偏好新增和替换由旅行消息处理流程内部调用。

所有接口从现有 Session 或游客 Cookie 解析身份。服务端不接受客户端传入 `userId` 或 `guestId`。越权删除统一返回不存在。

列表按以下顺序输出：出发城市、预算、节奏、兴趣、限制；同类按更新时间倒序。

## 自然语言管理

旅行对话优先识别：

- “你记住了什么”
- “我的旅行偏好是什么”
- “忘掉我不吃辣”
- “不要再记住成都出发”

查看时最多返回八项摘要，并提供打开“我的偏好”账户面板的操作。删除指令只有唯一匹配时执行；多个候选时轻量追问，找不到时明确说明没有这项记忆。查看和删除不会生成新行程版本。

新增事件：

- `travel.memory.updated`：保存、替换或删除完成。
- `travel.memory.question`：删除目标不明确。

## 账户面板

侧边栏仍固定为：

1. 开始出发吧
2. 历史记录
3. 我的收藏

不增加 Memory 主入口。点击侧边栏底部头像打开轻量账户面板：

- 登录用户显示邮箱、退出和“我的偏好”。
- 游客显示登录入口、“我的偏好”和“登录后可跨设备保留”。
- “我的偏好”展开五类偏好列表。
- 每项提供明确的删除按钮和可访问名称。
- 空状态显示“还没有长期偏好，正常规划时我会逐渐了解你”。

删除采用立即请求；成功后从列表移除，失败时保留并提示。长期偏好数量很少，第一版不增加搜索、分页、编辑表单或独立页面。

## 处理流程

旅行消息进入后：

```text
消息接收
  → 查看/删除 Memory 意图？
      → 是：执行管理操作并结束任务
      → 否：并行执行候选偏好提取
  → 读取当前身份 Memory
  → 按优先级合并 Planner 上下文
  → 正常追问或生成行程
  → 校验并保存提取结果
  → 响应附带轻量“已记住”提示
```

偏好提取失败不能导致旅行规划失败。Memory 数据库读写失败时使用本次明确输入继续规划，并记录不含用户原文的结构化错误日志。

## 隐私与安全

- 只保存五类旅行相关偏好，不提取健康诊断、政治、宗教、身份证件、支付信息或精确住址。
- “轮椅出行”等必要可达性限制可以保存，但不推断疾病或健康状态。
- 日志只记录 memory kind、操作结果和耗时，不记录原始用户消息或完整 value。
- 用户可逐项删除；账户删除时 Memory 级联删除。
- Memory 不参与广告、用户画像出售或与第三方 MCP 共享；只有生成具体查询所必需的当前需求才会发送给对应供应商。

## 测试

后端覆盖：

- 五类候选解析、Schema 校验、置信度门槛和非旅行敏感信息拒绝。
- 单值覆盖、多值去重、明确否定删除。
- 游客和用户身份隔离。
- 游客登录归并、账户优先及事务回滚。
- Memory 只填充当前行程缺失字段。
- 当前明确输入覆盖 Memory。
- 提取失败不影响正常规划。
- 查看和删除不创建 `TripVersion`。

前端覆盖：

- 游客和登录账户面板均可进入“我的偏好”。
- 分组列表、空状态、删除成功和失败回滚。
- `travel.memory.updated` 轻提示不会生成额外行程卡。
- 键盘操作、按钮可访问名称和移动端账户面板。

真实验收：

1. 游客说“我一般从成都出发，我不吃辣”。
2. 新建旅行，只说“十月想去首尔三天”，确认 Planner 自动采用成都和不吃辣。
3. 本次明确说“这次从上海出发”，确认上海优先且不会被成都覆盖。
4. 登录后确认游客偏好归并。
5. 从账户面板删除“不吃辣”，新行程不再自动带入。
6. 说“你记住了什么”和“忘掉成都出发”，确认不生成新报告。

## 不在本切片范围

- 向量数据库或语义检索。
- 保存完整对话摘要。
- 自动推断人格、消费能力、健康状况或人口属性。
- 偏好版本历史、恢复和跨账户共享。
- 标签、搜索、分页和独立 Memory 页面。
