# KoreaMate 第八阶段 8D：旅游知识库与 RAG 检索设计

## 1. 目标

在不增加用户操作负担的前提下，为旅行规划增加可追踪、可隔离、可降级的旅游知识检索能力。系统同时收录已核验的公共地点事实和用户主动导入的私人攻略经验，并在 Planner 输入和用户界面中明确区分两类内容。

本阶段使用从魔搭下载的 `BAAI/bge-m3` 生成中韩文多语言向量，使用 PostgreSQL `pgvector` 完成相似度检索。模型在独立的本地 Python 服务中运行，不依赖付费 Embedding API。

## 2. 范围

### 2.1 纳入范围

- 将 Kakao、韩国旅游数据等已有地点来源转换为公共官方知识。
- 将用户主动导入的小红书攻略解析结果转换为私人攻略知识。
- 使用 BGE-M3 对知识分段和用户查询生成 1024 维向量。
- 分别检索公共事实与当前身份可见的私人攻略。
- 将检索结果以结构化上下文提供给 Planner。
- 保存来源、抓取时间、有效期、可信类型和向量模型版本。
- 在模型或向量数据库不可用时可信降级。
- 支持知识删除、重新向量化和用户隔离测试。

### 2.2 不纳入范围

- 自动爬取小红书或其他内容平台。
- 将私人攻略匿名汇总为公共数据。
- 训练或微调 BGE-M3。
- 第一版混合稀疏检索、独立 reranker 或专用向量数据库。
- 将完整版权内容展示给其他用户。

## 3. 知识分类与可信语义

### 3.1 公共官方知识

公共知识来自系统已接入且可追踪的地点 Provider。内容可以包括地点名称、中文名称、地址、坐标、分类、地图链接以及 Provider 返回的其他结构化事实。

- 可见范围：所有用户。
- 可信类型：`official_fact`。
- 用户文案：`已核验`。
- 必填元数据：Provider、外部标识、抓取时间、有效期。
- 过期处理：降低排序权重并显示“数据可能已变化”。

### 3.2 私人攻略经验

私人知识来自用户主动提交的链接、文本或图片，经现有攻略导入流程解析后写入。

- 可见范围：所属用户或当前访客身份。
- 可信类型：`personal_experience`。
- 用户文案：`小助理建议`或`攻略经验`。
- 不得表述为官方事实。
- 删除导入记录时同步删除正文、分段和向量。

游客身份对应的私人知识在登录迁移流程中转移到用户账号，迁移后不再保留双重归属。

## 4. 总体架构

```text
官方地点数据 ─→ 标准化 ─→ 公共知识文档 ─┐
                                            ├─→ BGE-M3 Embedding 服务 ─→ pgvector
用户攻略导入 ─→ 清洗分段 ─→ 私人知识文档 ─┘
                                                       ↓
用户旅行需求 ─→ 公共知识检索 + 本人私人知识检索 ─→ Planner ─→ 带可信状态的行程
```

系统由四个边界清晰的单元组成：

1. `KnowledgeIngestionService`：把既有地点和攻略解析结果转换为知识文档。
2. `EmbeddingClient`：通过 HTTP 调用本地 Python 服务生成向量。
3. `KnowledgeSearchService`：执行身份过滤、相似度检索、去重和过期降权。
4. Planner 集成层：只接收结构化检索结果，不直接访问知识表。

## 5. 数据模型

### 5.1 KnowledgeDocument

保存一个可独立管理的知识来源：

- `id`
- `kind`: `official_fact | personal_experience`
- `visibility`: `public | private`
- `userId` 或 `guestId`，公共知识为空
- `provider`
- `externalId`
- `sourceUrl`
- `title`
- `rawContent`
- `sourceFetchedAt`
- `sourceExpiresAt`
- `contentHash`
- `status`: `pending | ready | failed | deleted`
- `createdAt`、`updatedAt`

公共文档使用 `provider + externalId` 去重。私人文档使用所有者、来源和内容哈希去重。

### 5.2 KnowledgeChunk

保存可检索的内容单元：

- `id`
- `documentId`
- `sequence`
- `content`
- `metadata`，只保存 Planner 需要的结构化字段
- `tokenCount`
- `contentHash`

地点事实优先按一个地点一个 Chunk 处理。攻略按自然段与主题边界切分，避免机械截断地点名称和完整建议。

### 5.3 KnowledgeEmbedding

保存向量及生成版本：

- `chunkId`
- `model`: `BAAI/bge-m3`
- `modelVersion`
- `dimensions`: `1024`
- `embedding`: `vector(1024)`
- `status`: `pending | ready | failed`
- `attempts`
- `lastErrorCode`
- `embeddedAt`

同一 Chunk 可以在模型升级期间同时存在新旧版本；检索只使用当前激活版本。新版本完成后再切换，避免重建期间中断检索。

## 6. Embedding 服务

Embedding 服务作为独立 Python HTTP 服务运行：

- 模型通过魔搭下载到持久缓存，不提交 Git。
- 启动时加载 `BAAI/bge-m3`，CPU 和 GPU 使用相同接口。
- 提供 `/health` 和 `/embed`。
- `/embed` 接受一组文本并返回 1024 维归一化向量。
- 请求设置批量上限、文本长度上限和超时。
- 第一版只生成 dense embedding，不启用 sparse 和 ColBERT 输出。
- 模型信息通过健康检查返回，后端验证维度和版本后才写入数据库。

本地开发允许 CPU 推理。公网部署可以继续使用 CPU 容器；若延迟或吞吐不足，再单独升级到 GPU 实例，不改变业务接口。

## 7. 入库流程

### 7.1 公共地点

地点 Provider 成功更新 `PlaceSource` 后触发知识同步：

1. 读取规范化 Place 和最新来源。
2. 生成稳定文本和内容哈希。
3. 内容未变化时只刷新来源有效期。
4. 内容变化时更新文档和 Chunk，并将 Embedding 标记为 `pending`。
5. 后台任务调用 Embedding 服务并写入向量。

### 7.2 私人攻略

攻略确认卡完成后触发知识同步：

1. 保存原始导入来源和解析结果。
2. 以主题和自然段为边界切分。
3. 给每个 Chunk 写入所属身份、涉及地点和内容哈希。
4. 后台生成向量。
5. 用户删除导入内容时级联删除所有知识数据。

## 8. 检索与 Planner 数据流

1. Travel Provider 提取目的地、兴趣、预算、同行人和限制。
2. `KnowledgeSearchService` 使用原始问题与结构化需求组成检索文本。
3. Embedding 服务生成查询向量。
4. 数据库分别执行两次检索：
   - 公共官方知识，仅 `visibility=public`。
   - 私人攻略，仅匹配当前 `userId` 或 `guestId`。
5. 每类独立限制候选数量，避免攻略挤掉官方事实。
6. 按向量相关性、来源有效性和重复地点进行排序与去重。
7. Planner 接收两个数组：`officialFacts` 和 `personalExperiences`。
8. Prompt 明确要求：事实可以直接引用；经验只能作为建议表达。
9. 最终输出沿用第 8C 阶段的可信状态与来源链接规则。

第一版每类最多返回少量高相关 Chunk，避免扩大提示词和 LLM 成本。相似度未达到阈值的内容不进入 Planner。

## 9. 权限与隐私

- 所有私人知识查询必须在数据库条件中包含所有者身份，不在应用层查询后再过滤。
- 公共知识不得包含用户上传的原文或私人身份字段。
- 日志不记录完整私人攻略内容和向量。
- 用户删除数据时执行事务级联删除。
- 访客知识迁移复用现有登录归属迁移机制，并保证幂等。
- 任何未能确定归属的私人知识都不得参与检索。

## 10. 失败降级

- Embedding 服务不可用：记录可重试状态；规划退回现有地点关键词搜索和基础 LLM 规划。
- pgvector 扩展不可用：启动健康检查标记 RAG 不可用，不阻塞翻译与基础规划。
- 单条文档失败：只隔离该文档并指数退避重试。
- 查询向量超时：本次请求跳过 RAG，不重复生成整份行程。
- 过期来源：允许以较低权重参与检索，但必须携带 `stale=true`。
- Planner 不得因为没有检索结果而报错。

降级状态通过内部诊断接口暴露，不向用户展示技术错误堆栈。

## 11. 配置

新增配置项只包含运行所需地址和版本：

- `EMBEDDING_SERVICE_URL`
- `EMBEDDING_MODEL=BAAI/bge-m3`
- `EMBEDDING_MODEL_VERSION`
- `KNOWLEDGE_SEARCH_ENABLED`

模型缓存目录由 Embedding 容器负责，不写入 Web 或 API 的 `.env`。所有配置在启动时验证，缺失时进入明确的禁用状态。

## 12. 测试与验收

### 12.1 单元与契约测试

- 官方地点与私人攻略生成不同知识类型。
- 内容哈希相同不会重复创建 Chunk。
- Embedding 响应维度必须为 1024。
- 过期来源正确降权并标记 stale。
- Planner 上下文保持事实和经验两个独立数组。

### 12.2 集成测试

- 中文问题能召回对应韩文地点资料。
- 用户 A 无法检索用户 B 的私人攻略。
- 游客登录后可以检索迁移后的私人攻略。
- 删除攻略后正文、Chunk 和向量立即不可检索。
- 模型版本切换期间旧版本仍可服务，切换后只使用新版本。

### 12.3 降级测试

- Embedding 服务关闭时仍可完成基础旅行规划。
- pgvector 查询失败时不会影响翻译功能。
- 单条文档向量化失败不阻塞其他文档。

### 12.4 用户验收

- 规划结果能利用用户导入的攻略偏好。
- 官方事实继续显示“已核验”。
- 攻略经验不会被描述为官方结论。
- 用户无需理解或操作知识库即可获得更相关的行程。

## 13. 实施边界

本阶段先完成 dense vector 检索闭环和可信降级。只有在真实检索评测证明召回质量不足后，才引入 BGE-M3 sparse 输出或独立 reranker，避免过早增加部署复杂度。
